# Knowledge Lifecycle

The Project Brain Framework becomes more effective through active operation.

Its full value does not exist at initialization time. It emerges as real project work produces decisions, failures, corrections, reviews, design judgments, operational lessons, and other meaningful experience—and that experience is deliberately converted into durable project knowledge.

## Lifecycle

### 1. Bootstrap
The Project Brain begins with the minimum durable context required to work coherently:
- intent,
- scope,
- architecture,
- active constraints,
- current state,
- operating rules.

Bootstrap creates orientation, not maturity.

### 2. Operation
Real project work produces new information:
- architectural choices,
- implementation discoveries,
- bugs and failure modes,
- security findings,
- rejected approaches,
- design approvals and rejections,
- operational incidents,
- changing assumptions.

Most operational detail is transient. Only information with future decision value should survive.

### 3. Reflection
Before knowledge is persisted, ask:
- Does this explain a why that code alone cannot reveal?
- Does this prevent repetition of a meaningful failure?
- Does this preserve state, intent, or judgment that future work will need?

If the answer is no to all three, do not persist it merely for completeness.

### 4. Consolidation
Relevant experience is written to exactly one canonical destination.

Do not duplicate truth across documents. Other material should reference the canonical source.

### 5. Reuse
Future work loads the preserved knowledge through progressive disclosure and uses it to reduce rediscovery, avoid known failures, and make better decisions.

### 6. Correction
When reality invalidates existing knowledge, correct the canonical source deliberately.

Do not preserve outdated guidance merely because it was once true. Where historical reasoning remains valuable, retain it as history or a superseded decision rather than allowing it to masquerade as current truth.

## Compounding Project Intelligence

The framework calls the accumulated, reusable understanding of a project **Project Intelligence**.

Project Intelligence may include:
- product intent,
- architecture knowledge,
- decision rationale,
- known failure modes,
- successful and failed approaches,
- design language and judgment,
- security knowledge,
- operational knowledge,
- integration constraints,
- lessons from real use.

Its value compounds only when meaningful experience is actively curated.

Time alone does not create Project Intelligence.

## Completion rule

When a substantive task produces durable knowledge that should influence future decisions, preserving that knowledge is part of completing the task.

Brain maintenance is therefore part of engineering work, not optional documentation cleanup.

This rule is constrained by the anti-bloat principle: the framework must not persist information merely because work occurred.

## Intended effect

At initialization, the framework helps a project organize itself.

With sustained use, it increasingly helps the project understand itself.

The intended long-term effect is that meaningful experience reduces future uncertainty instead of disappearing between sessions, tools, agents, and team changes.
